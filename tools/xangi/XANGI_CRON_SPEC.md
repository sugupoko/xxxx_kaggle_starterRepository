# xangi 定期実行（cron / schedule）運用仕様書

*作成: 2026-08-08 / 実装: xangi の `src/scheduler.ts` (v0.49.6 時点 760行) + `src/cli/schedule-cmd.ts`*
*姉妹: LLM を使わない常駐デーモン型通知 → `tools/xangi/xangi_health_daemon.sh` / `CLAUDE_USAGE_SPEC.md`*
*オプション機能（xangi + Discord で bot を回す人向け）。導入は `tools/xangi/README.md`*

## 0. これは何か

**「決まった時刻に Claude（エージェント）を起こして、仕事をさせ、結果を Discord へ投稿させる」** 仕組みの仕様と運用ノウハウ。
定点観測（Kaggle新着監視・メタ環境監視）、長時間ジョブの起動と見張り、自律ループの watchdog などを全部これで回している。

**重要な前提**: 定期実行には**2系統**あり、用途で使い分ける。

| | **xangi cron**（本書） | **常駐bashデーモン**（`xangi_health_daemon.sh` など） |
|---|---|---|
| 実行主体 | Claude エージェント（毎回LLMが動く） | 素のスクリプト（LLM不使用） |
| 向く仕事 | 判断・要約・次の一手を考える | 定型情報の垂れ流し・監視・キュー消化 |
| コスト | レート制限を消費 | ゼロ |
| 生存性 | xangi プロセスが生きていれば発火 | nohup常駐＝**再起動で死ぬ**（cronで復活させる） |
| 落とし穴 | 実行中の再発火はスキップ（§5.2） | ロックファイル管理 |

→ **定型の垂れ流しはデーモン、判断が要る所だけ cron**。両者を組み合わせる**ハイブリッド**が最も安定（§6）。

## 1. アーキテクチャ

```
xangi プロセス（常駐）
 └─ Scheduler (src/scheduler.ts)
      ├─ 永続化: <cwd>/.xangi/schedules.json （ファイル watch で外部変更も自動反映）
      ├─ node-cron でジョブ登録（timezone は Asia/Tokyo 固定 ※下の注）
      └─ 発火 → executeJob()
            ├─ 再発火ガード: runningJobs に居たら skip（§5.2）
            └─ executeJobInner() → agentRunner(prompt, channelId)
                  = Claude を起動しプロンプトを実行 → 応答をそのチャンネルへ投稿
                  ・一時的ネットワークエラーは15秒後に1回だけ自動リトライ
                  ・agentRunner 未登録時は素のメッセージ送信にフォールバック
```

**要点**
- スケジュールの実体は「**cron式＋プロンプト文字列＋投稿先チャンネルID**」の3つ組。プロンプトが仕様書そのもの＝**ここに全部書く**。
- **常に agent モード**で走る（単なる文字列送信ではなく、毎回 Claude がツールを使って仕事をする）。
- タイムゾーンは **Asia/Tokyo 固定**（cron式は JST で書く）。
  - ※ これは node-cron の `timezone` オプション（Node 内蔵の ICU で解決）の話。**シェルの `TZ=Asia/Tokyo` とは別物**。
    zoneinfo の無いコンテナでは `TZ=Asia/Tokyo date` は黙って UTC を返す（9 時間ズレる）ので、
    スクリプト側で JST が要るときは `date -u -d '+9 hours'` / `timezone(timedelta(hours=9))` で出す
- 保存先は起動ディレクトリの `.xangi/schedules.json`。**プロジェクトごとに独立**。

## 2. スケジュール種別

| type | 指定 | 用途 |
|---|---|---|
| `cron` | cron式（5フィールド） | 定期実行。本命 |
| `once` | 実行時刻 ISO8601 | 一回きり（リマインダー） |
| `startup` | なし | xangi 起動時に1回実行。**再起動後の自動復旧に有効** |

## 3. コマンド（全部 Bash から `xangi-cmd`）

```bash
# 一覧（ID・cron式・投稿先・プロンプト全文が見える）
xangi-cmd schedule_list

# 追加：cron式で指定（本命。--input の先頭に "cron <式> " を付ける）
xangi-cmd schedule_add --channel <チャンネルID> --input "cron 0 * * * * <プロンプト全文>"

# 追加：自然言語でも書ける
xangi-cmd schedule_add --channel <ID> --input "毎日 9:00 おはよう"
xangi-cmd schedule_add --channel <ID> --input "毎週月曜 10:00 週次MTG"
xangi-cmd schedule_add --channel <ID> --input "30分後 ミーティング"     # once
xangi-cmd schedule_add --channel <ID> --input "15:00 レビュー"          # once（過ぎてたら明日）
xangi-cmd schedule_add --channel <ID> --input "2026-08-10 15:00 締切"   # once
xangi-cmd schedule_add --channel <ID> --input "起動時 <プロンプト>"      # startup

# 削除 / 有効・無効トグル
xangi-cmd schedule_remove --id <スケジュールID>
xangi-cmd schedule_toggle --id <スケジュールID>
```

- `--channel` 省略時は実行中チャンネル。CLI 単体実行では必須。
- cron式は `node-cron` 準拠の5フィールド（`分 時 日 月 曜`）。`*/30 * * * *`、`0,30 7-12 * * *`、`14,44 * * * *` などが使える。
- **プロンプトはシェル引数なので改行を含められる**が、`"` のエスケープに注意。長文は一気に1行で書くのが安全。

## 4. プロンプト設計の定石（ここが本体・最重要）

cron の質は**プロンプトの書き方で決まる**。運用で確立したパターン:

### 4.1 冒頭にラベルを付ける
`[定点観測:メタ環境(毎時)]` のように角括弧の識別子から始める。`schedule_list` の可読性が段違い。

### 4.2 「変化がない時は無投稿」＝空文字を返させる
毎回発火して毎回喋ると通知が汚染される。**新着なしなら何も書かず空文字だけを返す**と明示する:
```
【重要】出力が空(=新着なし)の場合は何も書かず空文字だけを返すこと
(挨拶も絵文字も一切書かない=無投稿にする)
```
「変化があった時だけ詳しく、ほぼ変化なしなら一言だけ」という**2段階の粒度指定**も併用する。

### 4.3 取りこぼし対策で「多重発火＋初回だけ投稿」
1日1回だと xangi が落ちていた時に丸ごと落とす。**日中に何度も発火させ、新着があった初回だけ投稿**させる（§4.2の空文字ルールとセット）。
実例: `0,30 7-12 * * *`（7〜12時の毎時0分・30分＝12回）。
```
このcronは取りこぼし対策で日中複数回発火する設計なので、新着がある初回だけ投稿されればよい。
```

### 4.4 長時間処理は「nohup で投げて即応答」
**エージェント実行のタイムアウトは既定30分**（env `TIMEOUT_MS`）。超えそうな処理は必ずバックグラウンド化:
```
nohup python3 <重い処理> > /tmp/<name>.log 2>&1 & を起動し即座に「開始」と短く返答
(長時間処理のためタイムアウト回避)。完了後(数分〜十数分)に /tmp/<name>.log の最終行を確認し…
```

### 4.5 冒頭に watchdog を差す（常駐デーモンの生存保証）
nohup 常駐は**再起動で必ず死ぬ**。専用 cron を増やさず、既存 cron の先頭に起動コマンドを1行足すのが定石（多重起動防止があるので毎回叩いて無害）:
```
【最初に必ず】nohup /path/to/<name>_daemon.sh >/tmp/<name>.log 2>&1 & を実行して生存を保証する
(多重起動防止内蔵なので毎回叩いてよい。「already running」なら正常。
 この件は報告不要、起動し直した場合のみ一言添える)
```

### 4.6 状態は外部ファイルに置く（cron は毎回まっさら）
発火のたびに**新しい文脈**で走る。前回との差分を見たいなら、スクリプト側に履歴ファイル（例: `history.tsv` に1行/実行を追記）を持たせ、プロンプトで「**末尾2行を読み比べろ**」と指示する。heartbeat ファイル・進捗ログ・キューTSVも同じ発想。

### 4.7 判断基準と禁止事項を明記する
自律ループを回させるなら「何を見て」「どう決めて」「何をやってはいけないか」を書く:
```
堅実hill-climb維持(BEST超えで昇格・後退なし)、勝手に爆発案へ切替えない、
ログ出力ON維持、<script>のロジックは勝手に大改造しない
```

### 4.8 期限付きループは自己削除させる
「10時間だけ見張る」等は、終了条件（`stop_at.txt` を now と比較）と**自分自身の削除**をプロンプトに埋める:
```
schedule_list で自分のIDを見つけ schedule_remove --id で自身を削除して終了
```

### 4.9 出力の人格・書式を固定する
`<bot名>の人格(一人称わたし/さん付け/絵文字)で簡潔に` のように毎回書く（cron は CLAUDE.md を読むとは限らない前提で自己完結させる）。
**Discord では Markdown 表が崩れる**ので、表データはコードブロック等幅か PNG（→ `AGENTS.md`）。

## 5. 落とし穴（実際に踏んだもの）

### 5.1 Claude Code 組み込みの `CronCreate` は発火しない
xangi はメッセージごとに `claude -p --resume` を起動して応答後に**終了**するため、「REPLが idle のとき発火」する in-memory cron は動く余地がない（2026-07-31 に確認、`CronList` は `No scheduled jobs`）。**必ず `xangi-cmd schedule_add` を使う**。

### 5.2 【最重要】再発火ガードによる永久沈黙
`executeJob()` は `runningJobs` に同じIDが居ると**そのまま skip** する。前回の agent 実行が何らかの理由で終わらないと、**以降の発火が永久にスキップされる**（2026-07-31、毎時のメタ定点観測が 7:00 JST を最後に全レーン沈黙）。
- **対処**: 詰まったら `schedule_remove` → `schedule_add` で**新IDに作り直す**。同一IDのまま `schedule_toggle` してもガードは解けない。
- **予防**: 1回の実行を短く保つ（重い処理は §4.4 の nohup 方式で即抜ける）。

### 5.3 仕込んだら発火確認をする
「追加した」で満足しない。**次の発火予定時刻に本当に鳴ったか**をチャンネルで確認する。無投稿設計（§4.2）だと沈黙と正常の区別がつかないので、初回だけは必ず投稿される条件で試すか、ログで確認する。

### 5.4 レート制限を食う
cron 発火は毎回 LLM 実行＝週次上限を消費する。毎時×複数レーンは効く。**定型の垂れ流しは cron ではなくデーモンへ**（→ 姉妹doc）。

### 5.5 その他
- タイムゾーンは JST 固定。UTC で考えない。
- `.xangi/schedules.json` は起動ディレクトリ単位。**別プロジェクトへは自動で引き継がれない**（移植は §7）。
- 一時的なネットワークエラーだけ15秒後に1回リトライ。**タイムアウトや利用上限はリトライされない**（その回は落ちるだけ）。

## 6. 推奨構成: cron × デーモンのハイブリッド

自律実験ループで確立した役割分担（実例: 前のコンペのルールベース AI の自動改良ループ）:

```
cron（毎時 7,27,47分）＝「考える係」
  進捗ログを読む → キューが空なら次の実験を1行だけ考えて queue.tsv に追記 → 短く報告
  （キューに未消化があれば "何も投稿せず空文字を返して終了"）

常駐デーモン ＝「回す係／報告係」
  queue.tsv を消化してベンチを実行 → 結果を discord_send で投稿
```
**判断が要る所だけ LLM、実行と報告は素のスクリプト**。これならデーモンが死んでも cron が気づけるし、cron が詰まってもデーモンは走り続ける。

## 7. 別プロジェクトへ移植する手順

1. **xangi をそのプロジェクトのディレクトリで起動**する（スケジュールは `<cwd>/.xangi/schedules.json` 単位＝自動的に独立）。
2. 監視/実行スクリプトを `tools/` に用意し、**単体で手動実行して出力を確認**（cron に載せる前に必ず）。
3. `xangi-cmd schedule_add --channel <ID> --input "cron <式> <プロンプト>"` で登録。プロンプトは §4 の定石を全部盛り込む（ラベル／空文字ルール／nohup／人格／判断基準）。
4. **次の発火時刻に鳴ったか確認**（§5.3）。鳴らなければ remove→add で作り直し（§5.2）。
5. 常駐デーモンを併用するなら、いずれかの cron の冒頭に watchdog 行を差す（§4.5）。
6. **ID・投稿先・watchdog を差した場所を記録に残す**（メモリ or リポジトリの運用メモ）。ID は作り直すたび変わるので、古いIDが書いてある文書は必ず更新する。

### 10.1 スケジュール（2026-09-06 実測）

投稿先は断りがなければ定点観測用チャンネル `<HEALTH_CHANNEL>`。

| `s_mus6lbve_e19a` | cron `*/30 * * * *` | 定点観測:RunPod残高 → **`<RUNPOD_CHANNEL>`** | `tools/runpod/rp_credit_watch.sh` |

**RunPod残高レーン（2026-09-12 追加・人間の依頼）**: 残高・稼働レート・前回比・**停止したまま残っている pod**を
30分ごとに `#runpod` へ1行で投稿する。金額計算は LLM にさせず `tools/runpod/rp_credit_watch.sh` の出力を正本とし、
エージェントは出力をそのまま流すだけ。**無投稿設計ではないので、30分来なければ沈黙＝異常**（残り日数レーンと同じ思想）。

- 検知したい無駄は「`stop` しただけで `delete` してない pod」。**保管料が $1/日 出続ける**（2026-09-03〜05 に4台で実際に $9.00 溶かした）
- 🔴 `pod list` は EXITED を出さないので、スクリプトは必ず **`pod list --all`** を使う（README §落とし穴）
- 閾値は env で変えられる: `RP_WARN_USD`（既定 20 / 🟡）・`RP_CRIT_USD`（既定 10 / 🔴）
- 状態は `tools/runpod/.rp_credit_watch.json`（前回残高と時刻）。**mtime = 最終実行時刻**なので沈黙時の切り分けに使える
- 🔴 `TZ=Asia/Tokyo` は使わない。このコンテナに zoneinfo が無く UTC を JST と誤表示する（9時間ズレる）

**2026-10-03 の沈黙（§5.2 を RunPod レーンで踏んだ記録）**: `s_mtxkumfs_hngf` は 10/03 13:30 の投稿を最後に
約5時間沈黙した。切り分けは「**Discord履歴 + state の mtime**」で確定できる — 登録は enabled のまま・スクリプトは
手で叩けば正常・プロセスも 9/25 から再起動なし（`runningJobs` はインメモリなので再起動していなければ詰まりは残る）。
13:30 以前にも 7:00・9:00・10:00・11:00・11:30 が飛んでおり、**全停止の前に間欠skipが先行していた**（これが前兆）。
`schedule_remove` → `schedule_add` で `s_mus6lbve_e19a` に作り直して復旧。
**沈黙中に残高が $21.07 → $12.86 まで落ちていた**（pod 3台 $2.30/h）。監視が止まると一番見たい局面が見えない。

**残り日数レーン（2026-09-06 追加・人間の依頼）**: 締切までの残り日数・経過%・フェーズを毎朝 8:00 に
`#remain` へ投稿する。日付計算は LLM にさせず `tools/deadline_countdown.py` の出力を正本とし、
エージェントは出力をそのまま流して一言添えるだけ。**無投稿設計ではないので、朝に来なければ沈黙＝異常**
（他の定点観測レーンと違い、静かな日と詰まりが見分けられる。これ自体が scheduler の生存確認になる）。

**定点観測・監視の 4 レーンの冒頭には、生存監視デーモンの watchdog 行が入っている**（§4.5）。
残り日数レーンは実行を短く保つため watchdog 行を入れていない（他レーンが日に 24 回以上叩くので冗長）。
絶対パスで叩くこと（cron の cwd は xangi 起動ディレクトリで、デーモンは別ディレクトリにあるため）:

```bash
setsid nohup <REPO>/tools/xangi/xangi_health_daemon.sh \
  >/tmp/xangi_health_daemon.boot.log 2>&1 </dev/null &
```

（必要な env は `tools/xangi/xangi.env` に書いておけば、プロンプトに並べなくてよい → `tools/xangi/README.md`）

- 保存先は **xangi の起動ディレクトリ** `$XANGI_ROOT/.xangi/schedules.json`。
  このリポジトリの中ではないので、git には乗らない。**ID の記録はこの表（運用リポジトリでは日報・運用メモ）が正本**。
- **ID は作り直すたびに変わる**。復旧したらこの表を必ず更新すること（§7-6）。
- ウォッチャー本体の仕様は `tools/xangi/KAGGLE_WATCH_SPEC.md`。
- **発火確認（§5.3）済み**: 2026-08-08 19:25 JST に `once` 型のテストジョブ（3 分後）を仕込み、
  予定時刻ちょうどに発火することを確認した（`once` は発火後に自動で登録から消える）。

### 10.2.1 2026-08-09 の誤報（監視役が狼少年になった記録）

**症状**: コンテナを 10:18 JST に再起動したところ、生存監視デーモンが起動**9 秒後**に
「[Kaggle Discussion] 最終実行から 15.4 時間経過」「[パブリックコード] 同」と通報した。

**原因**: `kaggle_watch_health.py` が **state ファイルの mtime だけ**を見ていた。だが
cron スケジューラは xangi プロセスの中にしか居ないので、

- xangi / コンテナが止まっていた間
- レーンがまだ登録されていなかった間（このときは 8/8 20:09 JST 登録・初回発火は 8/9 07:00 JST 予定）

は**そもそも発火しようがない**。この「発火できなかった時間」まで沈黙に加算していたため、
再起動のたびに必ず誤報が出る（＝再起動直後は 100% 鳴る）。§5.2 の本物の沈黙と区別がつかず、
狼少年になって本番の警報を無視させる方が危ない。

**対処**: 実効の沈黙時間を

```
min(state の古さ, xangi の稼働時間, レーン登録からの経過時間)
```

に変更（`xangi_uptime_h()` は `/proc/*/cmdline` から `dist/index.js` を引き当て、
`/proc/<pid>/stat` の starttime ＋ `/proc/stat` の btime で起動時刻を出す）。
抑制したときは **stdout には出さず stderr に理由を書く** ので、無投稿のまま
`/tmp/xangi_health_daemon.log` に「なぜ鳴らなかったか」が残る（デーモンが `2>>` している）。

**判断のポイント**: 誤報だと分かっても、**先に ID を作り直さない**こと。§5.2 の対処は
「詰まったときの」対処であって、再発火ガードは **xangi の再起動で自動的に解ける**
（`runningJobs` はインメモリ）。再起動直後に remove→add すると、直っていない問題を
直したと誤認したうえ、§10.1 の ID 表を無駄に書き換えることになる。
**まず次の発火予定時刻まで待って、本当に鳴らないかを見る**（§5.3）。

**動作確認済み（2026-08-09）**: ①再起動直後（稼働 0.4h）は無出力＋stderr に抑制理由
②`--hours 0.1`（稼働時間 > しきい値）にすると従来どおり検知して通報

### 10.2.2 2026-08-09 の真犯人（WSL2 の壁時計ジャンプで node-cron が発火を捨てていた）

**症状**: §10.2.1 で誤報を潰したあとも警報が続いた。よく見ると誤報ではなく、
**レーンが登録以来ただの一度も発火していなかった**（state の mtime は手動実行した
8/8 19:17 JST のまま。xangi が起動していた時間帯だけで 8 スロット分が空振り）。

**原因**: `node-cron` の **missed execution 判定**。node-cron は `setTimeout`（＝単調時計）で
次スロットまで寝て、起きた時に**壁時計**と予定時刻を比べる。遅刻が
`missedExecutionTolerance`（**既定 1 秒**）を超えると、**実行せず missed 扱いで捨てる**。

この箱は WSL2 の VM 上にあり、省電力でゲストが小刻みに凍る。凍っている間、
単調時計は止まるが壁時計はホストに合わせて進むので、**壁時計だけが前へ飛ぶ**:

```
CLOCK STEP: wall+2839ms mono+1001ms   ← 34 秒ごとに約 +1.8 秒（≒5%）
```

寝ている時間が長いほど遅刻が積み上がる。**15 分間隔のレーンは毎回およそ 50 秒遅刻**するので、
1 秒の許容量では 100% 捨てられる ＝ **永久に沈黙する**。1 分間隔の cron でようやく
「たまに通る」レベル（実測 3 スロット中 1 回だけ発火）。

**実証**（同一プロセスで `* * * * *` を 2 本、tolerance だけ変えて 3 分回した）:

| | 03:23:01 | 03:24:03 | 03:25:03 | 計 |
|---|---|---|---|---|
| 既定（1s） | ✅ | ❌ missed | ❌ missed | **1** |
| 55s 許容 | ✅ | ✅ | ✅ | **3** |

**対処**（`src/scheduler.ts`）: 2 段構え。

1. `missedExecutionTolerance: 60_000` を付けて登録する。node-cron は
   `遅刻 <= 許容量 && 遅刻 < 次スロットまでの間隔` の**両方**を要求するので、
   広げても発火予定を追い越して二重に走ることはない。
2. 発火まで 2 分以上あるジョブは 30 秒ごとに `stop()`→`start()` でタイマーを張り直す。
   1 回の睡眠が最長 150 秒に制限され、遅刻が数秒までしか積み上がらなくなる
   （張り直さないと、夜間の長い空き時間で遅刻が数十分に育ち、朝いちのスロットを落とす）。
   **発火直前は触らない**——張り直すとそのスロットを取りこぼすため。

回帰テストは `tests/scheduler-clock-drift.test.ts`。

**教訓**: 「cron が沈黙している」と聞くと §5.2 の再発火ガードを疑いたくなるが、
**ID を作り直しても直らないなら別の犯人**。作り直す前に、まず
「そもそも node-cron 自身が発火しているか」を最小プロセスで確かめる
（1 分 cron を仕込んで数分眺めるだけで分かる）。§5.3 の発火確認はここでも効く。

### 10.2.3 2026-08-11 の再発（通報しても直らない／そもそも直す手が無かった）

**症状**: §10.2.2 で node-cron 側を直したのに、3 日続けて「こわれてる」と言われた。
8/10 はコードレーンが 7:45 に 1 回だけ通り、8/11 は両レーンとも 1 度も発火しなかった。

**原因は 2 つ重なっていた**:

1. **修正が反映されていなかった**。node-cron の修正は `dist/` に入っていたが、
   xangi プロセスは 8/9 のまま。**再起動しないと効かない**のに、この箱には
   supervisor が居ないので誰も再起動できなかった（§10.3）。
2. **VM ごと凍る時間帯は、遅刻許容量では救えない**。壁時計ジャンプ（§10.2.2）は
   「遅れて起きる」問題なので tolerance で救えるが、WSL2 が発火時刻を**丸ごと跨いで
   凍る**と、そのスロットは端から存在しなかったことになる。監視デーモンは
   それを検知して**通報していたが、通報だけでは何も取りに行かない**。

**対処 A: レーンのバックストップ**（`xangi_health_daemon.sh` の `drive_lanes`）

デーモンが「発火窓の中でレーンの state が 1.5h より古い」と見たら、通報するだけでなく
`xangi-cmd trigger` で**そのレーンのターンを直接起こす**。デーモンは単調時計に頼らず
「起きたときの壁時計」だけを見るので、凍っても取りこぼさない。

- 判定は `kaggle_watch_health.py --stale-lanes`（通報用の `--auto` と違い、
  **xangi 稼働時間による抑制をかけない**。抑制は「鳴らすべきか」の判断であって
  「取りに行くべきか」の判断ではない）
- プロンプトと投稿先は `.xangi/schedules.json` を唯一の正とする（二重管理しない）
- 同じレーンを起こし直す最短間隔は 90 分（`LANE_MIN_INTERVAL`）
- ウォッチャーは差分だけを出す設計なので、cron が先に走っていれば state が新しく、
  バックストップは黙る＝**二重投稿にならない**
- **`TRIGGER_ENABLED=true` が必要**（`.env`。起動時にしか読まれない）

**対処 B: supervisor を置く**（`tools/xangi/xangi_supervisor.sh`）

この箱に supervisor が居ないことが、①「再起動が要る修正が死蔵される」
②「`system_restart` が片道切符」の両方の根っこだった。PID 1 直下に
`while true` で xangi を抱える常駐を置いて解消する。

```bash
setsid nohup tools/xangi/xangi_supervisor.sh >/dev/null 2>&1 </dev/null &
tools/xangi/xangi_supervisor.sh --stop     # supervisor だけ止める
```

当時は `pkill -f 'dist/index\.js'` で旧プロセスを掃除していた（自分の cmdline に `dist/index.js` を含まないので自爆はしない）。
テンプレート版は AGENTS.md ルール 8 に合わせ、**`pgrep` の結果を cwd = `$XANGI_ROOT` で絞ってから PID 指定で kill** する
（同じコンテナの別の xangi を巻き込まないため）。
`BOOT_DELAY` は「supervisor を仕込んだターンの応答が Discord に届く猶予」。

**教訓**: 監視は「気づく」までしかやらない。**気づいた後に手を動かす経路**（trigger）と、
**直した物を反映する経路**（supervisor）が無いと、正しい通報が毎日鳴るだけになる。

### 10.4 監視デーモン（`tools/xangi/xangi_health_daemon.sh`）

§6 の役割分担そのもの。**検知と通報は LLM を通さない**ので、cron が全滅しても鳴る。
デーモンは **2 つ**を見張る（②③の詳細は `tools/xangi/CLAUDE_USAGE_SPEC.md`）:

```
常駐デーモン（LLM不使用・15分毎）＝「見張り係」
  ① kaggle_watch_health.py --auto → cron が沈黙していたら <HEALTH_CHANNEL> へ
  ② claude_usage.py --check       → Claude の使用率がしきい値を跨いだら <USAGE_CHANNEL> へ
  ③ USAGE_DAILY_HOUR 時台の初回だけ → 使用量スナップショットを <USAGE_CHANNEL> へ（既定は無効）

cron 4レーン（LLM）＝「仕事係 ＋ デーモンの watchdog」
  各レーンの冒頭で setsid nohup デーモン起動（多重起動は flock で防止＝毎回叩いて無害）
```

> ⚠️ **デーモンのスクリプトを書き換えたら必ず再起動する。** bash は実行中のファイルを
> 逐次読むので、走ったまま編集すると途中から壊れた内容を読む。停止は PID 指定で行うこと
> （`pkill -f xangi_health_daemon.sh` は**自分のコマンド行にもマッチして自殺する**）。
> テンプレート版は `/tmp/xangi_health_daemon.pid` を書くので `kill -TERM "$(cat /tmp/xangi_health_daemon.pid)"`。
> 2026-08-09 の修正で sleep をバックグラウンド＋`wait` にしたので、TERM は即座に効く（それ以前は sleep の終わりまで保留された）。

**判定は時間帯で切り替える**（`--auto`）。監視レーンは 7〜12 時 JST しか発火しないので、
固定しきい値だと夜通し誤検知するか、鈍くしすぎて 1 日気づけないかのどちらかになる:

| いまの JST | しきい値 | 根拠 |
|---|---|---|
| 08:00〜13:59 | **1.5h** | この時間帯は 30 分毎に発火しているはず |
| それ以外 | **26h** | 丸 1 日ぶんの発火窓を落としたら異常 |

**通知の抑制**: 同じ異常を鳴らし続けないよう、`/tmp/xangi_health_daemon.state` に
「最後に通知した内容の md5 ＋ 時刻」を持ち、**内容が変わったときと 6 時間経過時だけ**再通知する。
異常 → 正常に戻ったら **復旧通知を 1 回だけ**出す。

**動作確認済み（2026-08-08）**: ①正常時は無通知 ②state を 48h 古くすると検知＋通知
③同じ異常の連投は抑制 ④mtime を戻すと復旧通知 ⑤二重起動は `already running` で拒否
⑥`setsid` 起動後に **PPID=1** を確認（Discord のターンと一緒に死なないこと）。

**デーモンが死ぬ条件と復活経路**:
- xangi 再起動 / コンテナ再起動で死ぬ（nohup 常駐なので）
- → `startup` レーンが再起動直後に起こす。加えて cron 4 レーンが毎回叩くので日中は 24 回以上の復活機会がある
- → さらに日次 13:05 のレーンが「デーモンがちょうど 1 本動いているか」を見て、落ちていれば報告する

**残る弱点（正直に）**: xangi プロセス自体が落ちるとデーモンの `discord_send` も失敗する
（`/tmp/xangi_health_daemon.log` に `send failed` が残るだけ）。ただしその場合は bot 全体が沈黙するので、
人間側が先に気づく。ここを自動化するなら xangi の外側（ホスト側 cron / systemd）に監視役が要る。

**ログ**: `/tmp/xangi_health_daemon.log`（1MB を超えたら末尾 500 行に切り詰め）/ 起動ログ `/tmp/xangi_health_daemon.boot.log`

### 10.3 環境の注意（実際に踏んだもの）

- xangi の実行ユーザーの HOME と、Kaggle 認証の置き場がズレていた（`kaggle.json` が別ユーザーの HOME 側）。
  ウォッチャーには `KAGGLE_CONFIG_DIR` を渡す（`tools/xangi/KAGGLE_WATCH_SPEC.md`）
- cron のプロンプトには **`cd <REPO> &&` を必ず前置**する（`<REPO>` はこのリポジトリの絶対パス）。
  cron の cwd は xangi 起動ディレクトリなので、これが無いと `tools/*.py` を見つけられない
- コンテナのシステム時刻は **UTC**（`ls` の表示も UTC）。cron 式は **JST** で書く。読み替えを間違えない
